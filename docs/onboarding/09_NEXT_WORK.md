# 后续工作、优先级与两位成员分工

## 1. 分工原则

建议按“科研执行可信度”和“产品交付可用性”分两条主线，但每两周交换一次评审人。每项任务必须有代码/数据、自动化验证和文档三类产物，避免只熟悉自己一侧。

## 2. 建议负责人

### 成员 A：后端、模型与实验可信度

主要负责真实数据、真实 baseline、实验协议、结果评估、工作流可靠性和执行隔离。

### 成员 B：前端、API 与交付复现

主要负责三栏工作台、接口一致性、标准案例、Docker/CI、演示资产、文档和 PPT 素材。

共同负责：每个里程碑的端到端回归、结果真实性复核、GitHub PR 审阅和比赛表述。

## 3. P0：提交前必须完成

| 任务 | 当前证据/缺口 | 交付物 | 验收标准 | 建议负责人 |
|---|---|---|---|---|
| 固定三模式标准案例 | 模式有测试，但缺统一冻结案例 | 3 个输入 JSON、运行包、脱敏结果摘要 | 新环境逐一完成或明确降级，报告可导出 | A 主、B 验收 |
| 真实 Qwen 与外部源复验 | 本轮无 Key，只验证 fallback | Qwen ping、调用摘要、文献来源清单 | 固定模型/日期/时延，至少一条真实引用可追溯 | A 主、B 记录 |
| 新电脑 Docker 冷启动 | Compose 配置通过，未做冷启动录像 | 安装说明、启动日志摘要、录屏 | 从 clone 到页面可用不依赖开发者缓存 | B 主、A 复核 |
| 最终 demo freeze | freeze 工具存在，当前分支尚未生成标准包 | submission 目录、manifest、报告和复现命令 | hash 可核对，材料不含密钥和原始隐私数据 | B 主、A 复核 |
| 失败路径演示 | 本地有 failed/paused 测试状态 | retry/skip/pause/recover 演示案例 | 能解释错误分类和不可跳过的关键步骤 | B 主、A 复核 |
| 比赛口径清单 | 合成/真实边界容易被误讲 | 一页“可说/不可说”说明 | PPT、README、答辩口径一致 | 共同 |

## 4. P1：提升科学可信度

| 任务 | 当前证据/缺口 | 交付物 | 验收标准 | 建议负责人 |
|---|---|---|---|---|
| 接入真实地震数据子集 | 当前只有合成波形 | 数据下载/校验脚本、许可证、数据卡 | 固定 hash，event-level 防泄漏划分，仓库不直接塞大数据 | A |
| 固定真实公开 baseline | 候选发现不等于可运行 | 锁定 repo commit、环境、命令、指标 | 团队两台机器结果误差在约定范围内 | A |
| 独立测试集与重复实验 | 当前单次确定性 harness | 多随机种子、置信区间、混淆矩阵 | 报告不只展示最好一次 | A |
| 生产级执行隔离 | 当前为 AST + 白名单 + `-I` + 超时 | 独立受限容器、禁网、只读挂载、CPU/内存/时长限制 | 安全测试确认越权文件/网络/进程操作被阻断 | A 主、B 集成 |
| 文献与主张人工抽检 | 自动核验不能证明科学正确 | 抽样表、专家结论、修订记录 | 核心结论有原文定位和人工签字/确认 | 共同 |
| 成本与时延基线 | 历史记录零散 | 每 agent 调用数、token、时延、失败率 | 标准案例可估算时长和成本 | A 采集、B 展示 |

## 5. P2：工程与体验

| 任务 | 当前证据/缺口 | 交付物 | 验收标准 | 建议负责人 |
|---|---|---|---|---|
| CI | 本轮主要靠本机验证 | GitHub Actions 后端/前端/build/secret scan | PR 自动检查，失败禁止合并 | B |
| 拆分超大文件 | workflow、report writer、Workbench 较大 | 按职责拆模块，保持公开接口 | 全量测试不变，单文件职责清晰 | A 拆后端、B 拆前端 |
| API schema 自动同步 | Python/TypeScript 手动同步 | OpenAPI 生成类型或校验脚本 | schema 变更能在 CI 中发现前端漂移 | B |
| 运行数据分层 | 开发/测试/演示状态混在同一目录 | `data/dev`、`data/test`、`data/demo` 约定 | 统计不会再把 pytest fixture 当真实运行 | B 主、A 迁移 |
| 可观测性 | 已有步骤事件和 LLM 日志，缺统一总览 | 脱敏运行 summary、错误码统计 | 无需读取原始 prompt 即可诊断流程 | A 后端、B 前端 |
| 文档持续更新 | 历史 handoff 过时 | 发布检查单和版本化状态页 | 每个里程碑更新 status/results/next work | B |

## 6. 建议前四周节奏

### 第 1 周

- A：选定真实地震数据候选与许可证，固定一个公开 baseline。
- B：完成新机器 Docker 冷启动、CI 草案和三模式输入模板。
- 共同：跑一次真实 Qwen discovery，复核文献和审计链。

### 第 2 周

- A：完成真实数据准备脚本和最小 baseline 复现。
- B：冻结三个标准案例，整理失败/恢复演示。
- 共同：评审数据泄漏、引用真实性和比赛口径。

### 第 3 周

- A：加入重复实验、混淆矩阵和受限容器原型。
- B：完善结果/限制展示、PPT 素材和 API 类型自动检查。
- 共同：用第二台机器复现。

### 第 4 周

- A：结果审计、成本时延和安全测试。
- B：最终 demo freeze、技术文档与答辩演练。
- 共同：完整 10 分钟演示、异常路径和彩排复盘。

## 7. 每项任务的完成定义

1. 代码或数据脚本已提交。
2. 有自动化测试或可重复命令。
3. 结果同时记录成功和限制。
4. README/onboarding/API 中受影响内容已更新。
5. 另一位成员能在不口头指导的情况下复现并签字确认。

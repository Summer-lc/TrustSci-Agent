# 可恢复任务生命周期设计

## 目标

让历史任务以具体研究名称展示，并为运行中的任务提供暂停和废除能力。用户离开页面或重启后端后，仍能从历史工作区恢复一个由用户主动暂停的任务并继续执行。

## 用户可见状态

- `created`：已创建，尚未开始。
- `running`：正在运行。
- `paused`：暂停。通过 `pause_reason` 区分用户暂停、人工审查和错误恢复。
- `completed`：已完成。
- `failed`：执行失败，可使用现有错误恢复机制。
- `abandoned`：已废除，保留记录但永久禁止继续。

运行中收到暂停请求时，状态仍为 `running`，同时 `control_action=pause`，前端显示“正在暂停”。当前原子步骤完成后，工作流进入 `paused/user`。废除请求会立即将状态设为 `abandoned`；工作流结束当前原子操作后必须停止推进，并且不得覆盖废除状态。

## 历史记录名称

新建任务时从规范化后的研究问题生成 `display_name`：去掉多余空白，最多保留 32 个字符，超出部分使用省略号。前端对旧快照兼容：缺少 `display_name` 时直接从 `question` 生成同样的显示名称，不再向用户展示 `run_id`。

## 后端接口

- `POST /api/runs/{run_id}/pause`：请求用户暂停。
- `POST /api/runs/{run_id}/resume`：仅继续 `paused + pause_reason=user` 的任务。
- `POST /api/runs/{run_id}/abandon`：立即标记为已废除。

三个接口均写入工作区快照和 `last_action`。已完成或已废除的任务不能暂停；非用户暂停不能调用普通继续；废除是终态。

## 工作流控制

经典工作流和 LangGraph 工作流共用 `ScientistWorkflow._step`，因此控制检查放在每个原子步骤开始前和成功结束后。暂停在安全边界生效，避免留下半写入步骤。恢复使用现有 `_resume_incomplete_pipeline`，根据已完成步骤跳过已有成果，从下一项继续，不清空历史步骤。

## 前端交互

- 运行记录首行显示具体名称，次行显示当前阶段和更新时间。
- 运行中显示“暂停”和“废除”。暂停请求提交后禁用重复操作并显示“正在暂停”。
- 用户暂停显示“继续运行”和“废除”。
- 人工审查暂停显示“查看并处理”，继续沿用原有审查按钮。
- 已废除只允许查看，不允许恢复执行。
- 后端重启后，缺失于内存但仍有快照的记录显示在同一历史区域；用户暂停任务提供“恢复并继续”。

废除操作使用二次确认，防止误触。废除不会删除工作区文件。

## 恢复流程

1. 暂停接口立即写快照。
2. 工作流到达安全边界后再次写入 `paused/user` 快照。
3. 同一后端会话中直接调用继续接口。
4. 后端重启后先由工作区恢复接口载入内存，再调用继续接口。
5. 恢复执行不清空已有论文、证据、实验或步骤记录。

## 验收标准

1. 历史记录不显示运行编号，显示具体研究名称。
2. 运行中可请求暂停，最终进入用户暂停状态。
3. 用户暂停任务可继续，且从未完成阶段接着执行。
4. 工作区恢复后可继续用户暂停任务。
5. 运行中或暂停中的任务可废除，废除后不能继续。
6. 人工审查暂停和错误恢复行为不回归。
7. 前后端测试、类型检查和生产构建通过。
